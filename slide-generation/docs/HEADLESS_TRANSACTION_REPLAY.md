# Integrated transaction replay

`src/headless/transaction-replay.ts` replays recorded canonical source operations through `JsxBackend`, the durable engine and mandatory Chromium checks. It does not run a model, reconstruct an actor activation, or fall back to live inference.

`buildIntegratedTransactionCassette({ initial, compatibility, provenance, commits, operations })` consumes the headless host's authoritative engine commit stream and completed backend/host operations. It checks the entire source hash chain. Accepted edits identify commits by transaction ID; input identifies its first exact Prompt and original slide; creation identifies the stable slide's first appearance. Reads are placed at the source revision actually returned, even when their completion callback arrives later. Every commit must have exactly one known operation. Missing, ambiguous, changed or unrecorded source states refuse cassette construction.

`replayIntegratedTransactions(cassette, backend, compatibility)` requires the exact initial source and a freshly initialized canonical backend. It executes input, hashline reads/edits, explicit creation/navigation, pause/resume and undo/redo. Existing `RecordedTools` verifies every read/edit result field and permits only bijective snapshot-handle and top-level transaction-UUID replacement after verifying source, revision, scope, hashes and all other result fields. Commit-return source snapshots are included, so later edits can use those handles. Source hashes are checked after every operation and at completion. Returned coverage explicitly lists observation tools omitted from transaction replay.

The real Chromium test `test/headless-transaction-replay.integration.test.ts` records and replays synthetic scripted operations: successful edits, an edit using a prior commit-return snapshot, a visual refusal, a role error, durable inputs, duplicate delivery, slide creation, navigation, undo and redo. It checks source identity, evidence retention and handle mapping, and refuses a broken commit chain, changed original input or unmatched commit. Its provenance is `synthetic-test`; it is not real-model quality or timing evidence.

Full actor replay remains a separate requirement. Strict provider replay rejects dynamic request-context differences. Reproducing actor requests requires recorded scheduler clock/tick inputs and verified historical tool-handle projection; ignoring changed timestamps, source fields or arbitrary context would conceal scheduling differences. Transaction replay must never be reported as full actor replay or as a live responsiveness comparison.
