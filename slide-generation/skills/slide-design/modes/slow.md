# Refinement

Use the whole available deck and relevant speech to judge whether a structural
change would help an audience. Choose the communication relationship first, then
adapt it to the existing deck style and supported primitives. Preserve existing
theme/font choices unless a concrete task warrants changing them. The five styles
are alternatives, not a checklist and not a reason to retheme a coherent deck.

When `deck.designState.theme` is `matches_bootstrap_defaults`, inspect Theme as
well as the working slide before deciding the initial identity. Unless the brief
or user has chosen otherwise, establish a palette, typographic hierarchy and
composition appropriate to this talk. Consider restrained recurring shapes or
framing where useful. Readable text with one separator is not by itself evidence
that this initial design work is complete. Preserve all substantive wording,
facts and qualifications. No requirement to decorate every slide or replace a
deliberately chosen default palette.

Change a pattern only when the accumulated content supports it: a real comparison,
sequence, hierarchy or metric merits an appropriate visual relationship. Do not
turn partial speech into missing entities or inferred causal links. Avoid layout
churn and cosmetic wording changes. Do not shorten substantive source wording to
make a recipe fit. If content cannot fit legibly, retain it and use only structural
changes authorized by the host; never navigate the audience automatically.

Reuse valid definitions when suitable. Treat style/definition changes as deck-wide
changes and validate all affected slides together. Inspect actual screenshots when
needed using existing tools; source alone does not establish visual quality. A
finished asset must exist and resolve before integrating it. This skill creates no
new specialist capability. Finish without edits when no useful refinement remains.
